### Câu 1: Clean Architecture là gì? Tại sao dùng cho project này?

**Trả lời:**

Clean Architecture chia hệ thống thành các lớp đồng tâm theo nguyên tắc: **lớp bên trong không bao giờ biết về lớp bên ngoài**.

```
API  →  Application  →  Domain
         ↑
   Infrastructure
```

- `Domain` — chứa Entity, Exception, Enum. Không tham chiếu project nào khác.
- `Application` — chứa Service, DTO, Interface. Chỉ tham chiếu `Domain`.
- `Infrastructure` — chứa Repository, DbContext, JwtTokenService. Tham chiếu `Application` + `Domain`.
- `API` — chứa Controller, Middleware. Tham chiếu `Application` + `Infrastructure` (chỉ để đăng ký DI).

**Lý do dùng:** Nếu ngày mai đổi SQL Server sang PostgreSQL, chỉ thay lớp `Infrastructure`. `Domain` và `Application` không bị ảnh hưởng vì chúng không biết database là gì.

**Trong project:** `ISinhVienRepository` được định nghĩa trong `Application/Interfaces`, cài đặt trong `Infrastructure/Repositories` — Service chỉ gọi interface, không biết EF Core tồn tại.

### Câu 2: Repository Pattern là gì? Khác gì với dùng DbContext trực tiếp?

**Trả lời:**

Repository là lớp **ẩn đi logic truy vấn database** phía sau một interface. Tầng Service chỉ gọi interface — không quan tâm SQL được viết như thế nào.

**Nếu inject DbContext trực tiếp vào Service:**
- Logic truy vấn rải khắp nơi, khó bảo trì.
- Không thể mock khi viết Unit Test (phải có database thật).
- Trộn lẫn business logic với truy vấn dữ liệu.

**Dùng Repository:**
- Toàn bộ truy vấn nằm trong một chỗ.
- Khi test, mock `ISinhVienRepository` thay vì database.
- Service chỉ gọi `uow.SinhViens.GetByMssvAsync(mssv)` — không cần biết SQL.

**Trong project:** `SinhVienRepository` kế thừa `BaseRepository<SinhVien>` (CRUD chung) và bổ sung `GetDetailAsync`, `GetPagedFilterAsync` cho nhu cầu đặc thù.

### Câu 3: Unit of Work là gì? Tại sao không inject từng Repository riêng?

**Trả lời:**

Unit of Work **gom tất cả repository dưới một kết nối database duy nhất** và commit tất cả thay đổi trong một transaction qua `CommitAsync()`.

**Nếu inject 3 repository riêng:**
```csharp
// BAD — 3 DbContext khác nhau, không cùng transaction
public SinhVienService(ISinhVienRepository sv, ITaiKhoanRepository tk, IGiaoVienRepository gv)
```
Mỗi repository tạo `DbContext` của riêng mình → chúng không thể tham gia cùng một transaction → nếu bước 2 thất bại, bước 1 đã commit rồi, dữ liệu không nhất quán.

**Dùng Unit of Work:**
```csharp
// GOOD — một DbContext chung
await uow.TaiKhoans.AddAsync(taiKhoan);
await uow.SinhViens.AddAsync(sinhVien);
await uow.CommitAsync(); // commit cả 2 hoặc không gì được lưu
```

**Trong project:** `UnitOfWork` dùng lazy initialization — repository chỉ được tạo khi lần đầu truy cập, giúp tiết kiệm bộ nhớ.

### Câu 4: Dependency Injection là gì? Được dùng ở đâu trong project?

**Trả lời:**

Dependency Injection (DI) là kỹ thuật **đưa dependency từ bên ngoài vào** thay vì để class tự tạo. Giúp loose coupling — dễ thay thế, dễ test.

**Không dùng DI (tệ):**
```csharp
public class AuthService()
{
    private readonly UnitOfWork _uow = new UnitOfWork(); // gắn chặt vào implementation
}
```

**Dùng DI (tốt):**
```csharp
public class AuthService(IUnitOfWork uow, IJwtTokenService jwtTokenService) { }
// IUnitOfWork được inject — có thể thay bằng mock khi test
```

**Trong project:** Tất cả Service, Repository, DbContext được đăng ký trong `AddApplication()` và `AddInfrastructure()` — `Program.cs` chỉ gọi hai method này, không tạo object thủ công.

### Câu 5: DTO là gì? Tại sao không trả Entity trực tiếp cho client?

**Trả lời:**

DTO (Data Transfer Object) là object chỉ chứa dữ liệu cần thiết để **giao tiếp giữa các tầng hoặc với client** — không chứa logic nghiệp vụ.

**Tại sao không trả Entity:**
- Entity thường có navigation properties vòng tròn → JSON serializer bị lỗi circular reference.
- Entity có thể chứa trường nhạy cảm (mật khẩu hash, refresh token) — nếu quên loại trừ là lộ dữ liệu.
- Client không nên biết cấu trúc database bên trong.

**Trong project:** `TaiKhoan` có trường `MatKhau` và `RefreshToken`. Nếu trả entity thẳng ra, client sẽ thấy hash mật khẩu. `TaiKhoanDto` không có hai trường này.

### Câu 6: AutoMapper là gì? Hoạt động như thế nào?

**Trả lời:**

AutoMapper là thư viện **tự động sao chép giá trị giữa hai object** có cấu trúc tương tự, tránh phải copy thủ công từng property.

```csharp
// Không có AutoMapper (dễ quên property, dễ lỗi)
var dto = new SinhVienDto
{
    Id    = sv.Id,
    HoTen = sv.TaiKhoan.HoTen,
    Email = sv.TaiKhoan.Email,
    // ... 10 dòng nữa
};

// Có AutoMapper
var dto = mapper.Map<SinhVienDto>(sv); // 1 dòng
```

Quy tắc ánh xạ được định nghĩa một lần trong `MappingProfile.cs`. Trường cùng tên được ánh xạ tự động; trường khác tên dùng `.ForMember(d => d.HoTen, o => o.MapFrom(s => s.TaiKhoan.HoTen))`.

**Trong project:** `SinhVien → SinhVienDto` cần lấy `HoTen` từ navigation property `TaiKhoan` — không thể ánh xạ tự động → khai báo tường minh trong `MappingProfile`.

### Câu 7: FluentValidation là gì? Khác gì với Data Annotation?

**Trả lời:**

FluentValidation là thư viện viết quy tắc kiểm tra dữ liệu đầu vào dưới dạng class riêng, tách biệt khỏi DTO.

**Data Annotation (hạn chế):**
```csharp
public class LoginRequestDto
{
    [Required]
    [MaxLength(50)]
    public string TenDangNhap { get; set; }
}
// Validation lẫn với DTO, khó test, không thể reuse logic phức tạp
```

**FluentValidation (tốt hơn):**
```csharp
public class LoginRequestValidator : AbstractValidator<LoginRequestDto>
{
    public LoginRequestValidator()
    {
        RuleFor(x => x.TenDangNhap).NotEmpty().MaximumLength(50);
        RuleFor(x => x.MatKhau).NotEmpty().MinimumLength(6);
    }
}
```

ASP.NET Core tự động chạy validator trước khi vào method controller → nếu thất bại trả HTTP 400 mà không cần viết thêm code kiểm tra.

### Câu 8: Global Exception Middleware hoạt động như thế nào?

**Trả lời:**

`GlobalExceptionMiddleware` bọc toàn bộ pipeline trong `try/catch`. Khi bất kỳ Service nào ném exception, middleware bắt và **ánh xạ sang HTTP status code tương ứng**.

```
Service ném NotFoundException
    → Middleware bắt → HTTP 404 + JSON { success: false, message: "..." }

Service ném BadRequestException
    → Middleware bắt → HTTP 400

Service ném ForbiddenException
    → Middleware bắt → HTTP 403

Exception lạ (bug)
    → Middleware bắt → HTTP 500 + "Đã xảy ra lỗi không mong đợi."
```

**Lợi ích:** Không cần `try/catch` trong từng controller. Service có thể ném exception tự nhiên, middleware lo phần HTTP. Toàn bộ response lỗi đều có cùng cấu trúc `ApiResponseDto`.

### Câu 9: JWT là gì? Token gồm mấy phần?

**Trả lời:**

JWT (JSON Web Token) là chuẩn truyền thông tin giữa các bên dưới dạng JSON được ký số. Token gồm **3 phần** cách nhau bằng dấu chấm:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← Header (base64)
.eyJzdWIiOiI0IiwicmxlIjoiU2luaFZpZW4ifQ  ← Payload (base64)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature (HMAC-SHA256)
```

- **Header:** Thuật toán ký (HS256) và loại token (JWT).
- **Payload:** Các claim — Id tài khoản, tên đăng nhập, vai trò, họ tên, thời hạn.
- **Signature:** HMAC-SHA256 của (Header + Payload) dùng secret key. Ngăn giả mạo nội dung.

**Quan trọng:** Payload **không được mã hóa** — ai cũng decode được. Chỉ có Signature mới đảm bảo tính toàn vẹn.

---

### Câu 10: Tại sao dùng JWT thay vì Session?

**Trả lời:**

| | Session | JWT |
|---|---|---|
| Lưu trạng thái | Server lưu session | Stateless — không lưu gì |
| Scale ngang | Cần sticky session hoặc Redis chung | Bất kỳ server nào cũng xác thực được |
| Hiệu suất | Mỗi request tra cứu session trong DB/Redis | Chỉ verify chữ ký bằng secret key |
| Thu hồi | Xoá session ngay | Phải đợi access token hết hạn (hoặc dùng blacklist) |

**Trong project:** Hệ thống chạy trên EC2 single server nên cả hai đều dùng được, nhưng JWT thể hiện khả năng scale và phù hợp với kiến trúc REST stateless hơn.

### Câu 11: Access token và Refresh token khác nhau như thế nào?

**Trả lời:**

| | Access Token | Refresh Token |
|---|---|---|
| Thọ | 60 phút | 7 ngày |
| Mục đích | Xác thực mỗi API call | Lấy access token mới |
| Nơi lưu (client) | Memory / localStorage | localStorage / HttpOnly cookie |
| Nơi lưu (server) | Không lưu (stateless) | Lưu trong bảng `tai_khoan` |
| Cấu trúc | JWT có payload | Chuỗi Base64 ngẫu nhiên 64 byte |
| Khi bị đánh cắp | Mất quyền tối đa 60 phút | Nguy hiểm hơn — cần xoay vòng |

**Lý do tách:** Token thọ dài tiện nhưng nếu bị đánh cắp, kẻ tấn công dùng được lâu. Token ngắn an toàn hơn nhưng phải đăng nhập lại liên tục. Kết hợp 2 loại là tradeoff tốt nhất.

### Câu 12: Refresh Token Rotation là gì? Tại sao phải làm vậy?

**Trả lời:**

Mỗi lần client gọi `/api/auth/refresh`, server **cấp cặp token MỚI** và **vô hiệu hoá token cũ ngay lập tức** bằng cách ghi đè trong database.

**Tại sao cần:**
1. Nếu refresh token bị đánh cắp, kẻ tấn công gọi `/refresh` trước → server cấp token mới cho kẻ tấn công và vô hiệu hoá token cũ.
2. Lần tiếp theo người dùng hợp lệ gọi `/refresh` → token không còn trong DB → thất bại → biết có xâm phạm → buộc đăng nhập lại.

**Trong project:**
```csharp
// AuthService.RefreshTokenAsync
taiKhoan.RefreshToken = refreshTokenMoi;   // ghi đè token cũ
await uow.CommitAsync();                   // lưu ngay — token cũ vô hiệu
return new LoginResponseDto { ... };       // trả token mới
```

### Câu 13: BCrypt là gì? Tại sao không dùng MD5 hay SHA256?

**Trả lời:**

BCrypt là **hàm băm mật khẩu** được thiết kế cố tình chậm, khiến brute-force không khả thi.

**MD5 / SHA256 (không an toàn để băm mật khẩu):**
- Tốc độ rất nhanh → GPU hiện đại thử hàng tỷ hash/giây.
- Không có salt → hai mật khẩu giống nhau cho cùng một hash → rainbow table attack.
- SHA256 của "Password@123" luôn là cùng một chuỗi ở mọi nơi.

**BCrypt (đúng cách):**
- Cost factor làm chậm mỗi lần băm (~100ms) → brute-force tốn hàng triệu năm.
- Tự thêm salt ngẫu nhiên → cùng mật khẩu cho hash khác nhau mỗi lần.
- `BCrypt.Verify()` so sánh an toàn, không lộ timing.

**Trong project:** `BCrypt.Net.BCrypt.HashPassword(dto.MatKhau)` khi tạo tài khoản; `BCrypt.Net.BCrypt.Verify(matKhauNhap, hashTrongDB)` khi đăng nhập.

### Câu 14: Tại sao đăng nhập sai tên và sai mật khẩu đều trả về cùng một thông báo?

**Trả lời:**

Để ngăn **Username Enumeration Attack** — tấn công dò tên đăng nhập.

**Nếu thông báo khác nhau:**
```
"Tên đăng nhập không tồn tại." → kẻ tấn công biết username sai → thử username khác
"Mật khẩu không đúng."         → kẻ tấn công biết username đúng → tập trung brute-force mật khẩu
```

**Nếu cùng thông báo:**
```
"Tên đăng nhập hoặc mật khẩu không đúng." → không lộ thông tin nào về username
```

Kẻ tấn công không biết username có tồn tại hay không → phải brute-force cả username lẫn mật khẩu → tốn gấp nhiều lần.

### Câu 15: Claims trong JWT là gì? Claim nào được lưu trong project?

**Trả lời:**

Claims là **các cặp key-value mô tả người dùng** được nhúng trong payload JWT. Server không cần tra database để biết thông tin cơ bản về người dùng.

**Claims trong project:**
```csharp
new Claim(ClaimTypes.NameIdentifier, taiKhoan.Id.ToString()),   // "sub": "4"
new Claim(ClaimTypes.Name,           taiKhoan.TenDangNhap),     // "name": "sv001"
new Claim(ClaimTypes.Role,           taiKhoan.VaiTro.TenVaiTro),// "role": "Sinh viên"
new Claim("ho_ten",                  taiKhoan.HoTen),            // "ho_ten": "Nguyễn Thị Hoa"
```

**Ứng dụng:**
- `[Authorize(Roles = "Admin")]` đọc từ claim `Role` → không query DB.
- `AuthController.Logout` đọc `NameIdentifier` để biết cần thu hồi token của ai.

### Câu 16: Phân quyền theo vai trò được thực hiện như thế nào?

**Trả lời:**

Dùng attribute `[Authorize(Roles = "...")]` trên controller hoặc action. ASP.NET Core tự động kiểm tra claim `Role` trong JWT trước khi vào method.

```csharp
[Authorize(Roles = "Admin")]                    // chỉ Admin
public async Task<IActionResult> Create(...)    // HTTP 403 nếu không phải Admin

[Authorize(Roles = "Admin,Giáo vụ")]            // Admin hoặc Giáo vụ
public async Task<IActionResult> GetPaged(...)

[Authorize(Roles = "Admin,Giáo vụ,Sinh viên")] // cả 3 vai trò
public async Task<IActionResult> GetById(...)
```

**Luồng:**
```
Request đến → JWT Middleware xác thực token → giải mã claim Role
           → [Authorize] so sánh Role với danh sách cho phép
           → Khớp: vào method | Không khớp: HTTP 403 Forbidden
```

### Câu 17: Token được lưu ở đâu phía client? Có an toàn không?

**Trả lời:**

**Có 2 lựa chọn phổ biến và tradeoff của chúng:**

| | localStorage | HttpOnly Cookie |
|---|---|---|
| Truy cập từ JS | Có (dễ đọc bằng JS) | Không (chỉ trình duyệt gửi tự động) |
| XSS Attack | Nguy hiểm — JS độc hại đọc được token | An toàn — JS không đọc được |
| CSRF Attack | An toàn — phải set header thủ công | Nguy hiểm — gửi tự động theo request |

**Trong project (React + Axios):** Access token lưu trong memory (Zustand store), refresh token trong localStorage. Khi F5 trang, dùng refresh token để lấy lại access token.

**Trả lời khi bị hỏi:** "Trong môi trường học thuật, chúng em dùng localStorage để đơn giản. Trên production thật, nên dùng HttpOnly Cookie cho refresh token để chống XSS."

### Câu 18: Làm sao hệ thống ngăn chặn SQL Injection?

**Trả lời:**

Entity Framework Core **tự động dùng parameterized query** cho mọi thao tác — không bao giờ nối chuỗi SQL trực tiếp.

```csharp
// EF Core dịch ra SQL parameterized
.FirstOrDefaultAsync(x => x.TenDangNhap == tenDangNhap)
// → SELECT * FROM tai_khoan WHERE ten_dang_nhap = @p0
// @p0 = "sv001" — dữ liệu không bao giờ nằm trong câu SQL

// Không dùng FromSqlRaw với dữ liệu không tin cậy
// → tức là project này hoàn toàn miễn nhiễm SQL Injection theo mặc định
```

Toàn bộ project không có câu lệnh `FromSqlRaw` hay nối chuỗi SQL thủ công → SQL Injection không thể xảy ra.

### Câu 19: Code First là gì? Khác gì Database First?

**Trả lời:**

**Code First:** Viết class C# (Entity) trước → EF Core tự tạo schema database qua Migration.

**Database First:** Thiết kế database trước → generate class C# từ schema.

**Tại sao chọn Code First:**
- Database schema được kiểm soát bởi code → dễ version control bằng Git.
- Migration tự động theo dõi sự thay đổi schema theo thời gian.
- Entity và database luôn đồng bộ — không thể quên update một trong hai.
- Dễ chuyển sang database khác hơn (chỉ đổi provider EF Core).

**Trong project:** Chạy `dotnet ef migrations add InitialCreate` → EF Core đọc Entity và Configuration → sinh file migration SQL → `dotnet ef database update` hoặc `MigrateAsync()` khi startup.

---

### Câu 20: AuditableEntity là gì? Tại sao mọi entity đều kế thừa nó?

**Trả lời:**

`AuditableEntity` là abstract class chứa 3 trường chung cho mọi bảng:

```csharp
public abstract class AuditableEntity
{
    public int Id { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime UpdatedAt { get; set; }
}
```

**Tại sao:**
- Mọi bảng đều cần `Id` (khóa chính), `CreatedAt` (khi tạo), `UpdatedAt` (khi sửa gần nhất).
- Kế thừa một lần, không phải copy 3 dòng vào 30 entity.
- `AppDbContext.SaveChangesAsync` tự set giá trị → không cần set thủ công ở tầng Service.
- `IRepository<T> where T : AuditableEntity` đảm bảo mọi entity đều có `Id` để truy vấn.

### Câu 21: IEntityTypeConfiguration là gì? Tại sao dùng thay vì Data Annotation?

**Trả lời:**

`IEntityTypeConfiguration<T>` là interface cho phép cấu hình ánh xạ Entity → bảng SQL trong một class riêng, tách biệt hoàn toàn khỏi Entity.

**Data Annotation (hạn chế):**
```csharp
public class SinhVien : AuditableEntity
{
    [Column("mssv")]
    [MaxLength(20)]
    public string Mssv { get; set; }
    // Domain Entity biết về Database → vi phạm Clean Architecture
}
```

**IEntityTypeConfiguration (đúng):**

### Câu 23: SaveChangesAsync hoạt động như thế nào? Tại sao phải gọi CommitAsync?

**Trả lời:**

EF Core theo dõi thay đổi qua **ChangeTracker**. Các method như `AddAsync`, `Update`, `Remove` chỉ **đánh dấu** entity vào ChangeTracker — chưa có SQL nào được gửi đến database.

```csharp
await uow.TaiKhoans.AddAsync(taiKhoan);   // ChangeTracker: Added
uow.SinhViens.Update(sv);                  // ChangeTracker: Modified
// Đến đây chưa có gì trong DB

await uow.CommitAsync();
// → AppDbContext.SaveChangesAsync()
// → EF Core dịch ChangeTracker → INSERT + UPDATE
// → Gửi một batch SQL đến database
// → Transaction tự động
```

**Trong project:** `CommitAsync()` trong `UnitOfWork` chỉ là wrapper của `context.SaveChangesAsync()` — nhưng qua UnitOfWork, tất cả repository dùng chung `context` nên commit một lần là đủ.

### Câu 24: Lazy Loading và Eager Loading khác nhau như thế nào?

**Trả lời:**

**Lazy Loading:** Navigation property chỉ được tải khi lần đầu truy cập → có thể dẫn đến N+1 query problem.

**Eager Loading (`.Include()`):** Tải navigation property cùng một lúc với entity chính trong một câu query.

**Project dùng Eager Loading:**
```csharp
// SinhVienRepository.GetDetailAsync
await DbSet
    .Include(x => x.TaiKhoan)    // JOIN tai_khoan trong cùng 1 query
    .Include(x => x.Lop)         // JOIN lop_sinh_hoat
    .FirstOrDefaultAsync(x => x.Id == id);
```

**Tại sao không dùng Lazy Loading:** Project tắt Lazy Loading theo mặc định (không cài `UseLazyLoadingProxies`). Eager Loading rõ ràng hơn — nhìn vào query biết ngay dữ liệu nào được tải.

### Câu 25: Xử lý Khoá ngoại vòng tròn (Circular FK) giữa SinhVien và LopSinhHoat như thế nào?

**Trả lời:**

`SinhVien.LopId → LopSinhHoat` và `LopSinhHoat.ThuKyId → SinhVien` tạo vòng tròn — không thể insert đồng thời.

**Giải pháp:** Insert 2 bước với nullable FK:

```sql
-- Bước 1: Insert SinhVien không có Lop
INSERT INTO sinh_vien (tai_khoan_id, mssv, lop_id) VALUES (4, '2100001', NULL)

-- Bước 2: Insert LopSinhHoat không có ThuKy
INSERT INTO lop_sinh_hoat (ma_lop, gvcn_id, thu_ky_id) VALUES ('KTPM2021A', 1, NULL)

-- Bước 3: Gán Lop cho SinhVien
UPDATE sinh_vien SET lop_id = 1 WHERE id = 1

-- Bước 4: Gán ThuKy cho Lop
UPDATE lop_sinh_hoat SET thu_ky_id = 1 WHERE id = 1
```

Cả `ThuKyId` và `LopId` đều được khai báo nullable trong Entity → EF Core cho phép insert với NULL.

### Câu 27: Quy trình tạo sinh viên mới hoạt động như thế nào? Tại sao cần 2 lần CommitAsync?

**Trả lời:**

Khi tạo sinh viên, cần tạo **hai bản ghi liên kết**: `TaiKhoan` và `SinhVien`.

**Tại sao 2 lần Commit:**
```csharp
// Bước 1: Tạo TaiKhoan trước — cần lấy Id sau khi lưu
var taiKhoan = new TaiKhoan { TenDangNhap = dto.TenDangNhap, VaiTroId = 3, ... };
```

### Câu 28: Công thức tính điểm tổng kết là gì? Tại sao chia tỉ lệ đó?

**Trả lời:**

```
DiemTongKet = DiemQT1 × 0.15 + DiemQT2 × 0.15 + DiemThi × 0.70
```

- **Quá trình 1 (15%):** Điểm giữa kỳ 1 — đánh giá học tập liên tục.
- **Quá trình 2 (15%):** Điểm giữa kỳ 2 — đánh giá tiến trình học.
- **Thi cuối kỳ (70%):** Đánh giá kiến thức toàn bộ môn học — trọng số cao nhất.

**Ví dụ thực tế trong seed data:**
```
Sinh viên 1: 8.0 × 0.15 + 7.5 × 0.15 + 8.5 × 0.70 = 1.20 + 1.125 + 5.95 = 8.275 ≈ 8.3 (Đạt)
Sinh viên 3: 4.5 × 0.15 + 5.0 × 0.15 + 3.0 × 0.70 = 0.675 + 0.75 + 2.10 = 3.525 ≈ 3.6 (Rớt)
```

Quy trình dưới 4.0 hoặc thi dưới 4.0 → rớt môn → đăng ký thi lại (`DanhSachThiLai`).

### Câu 36: AAA Pattern là gì? Cho ví dụ cụ thể.

**Trả lời:**

AAA = **Arrange (Chuẩn bị) / Act (Thực hiện) / Assert (Kiểm tra)** — cấu trúc chuẩn cho mọi test case.

```csharp
[Fact]
public async Task LoginAsync_DungThongTin_TraVeToken()
{
    // ARRANGE — chuẩn bị dữ liệu và mock
    var taiKhoan = new TaiKhoan
    {
        Id = 1,
        TrangThai = true,
        MatKhau = BCrypt.Net.BCrypt.HashPassword("Password@123"),
        VaiTro = new VaiTro { TenVaiTro = "Sinh viên" }
    };
    _mockTaiKhoanRepo.Setup(r => r.GetByTenDangNhapAsync("sv001"))
                     .ReturnsAsync(taiKhoan);
    _mockJwtService.Setup(j => j.GenerateAccessToken(taiKhoan))
                   .Returns("fake-access-token");

    // ACT — thực hiện hành động cần test
    var result = await _authService.LoginAsync(new LoginRequestDto
    {
        TenDangNhap = "sv001",
        MatKhau = "Password@123"
    });

    // ASSERT — kiểm tra kết quả
    result.AccessToken.Should().Be("fake-access-token");
    result.UserInfo.Should().NotBeNull();
}
```

1. **Docker Compose:** `healthcheck` gọi `/health` → xác nhận backend sẵn sàng trước khi frontend khởi động.
2. **Load Balancer / AWS:** Auto Scaling Group kiểm tra instance có đang healthy không.
3. **Monitoring:** Team ops gọi định kỳ để cảnh báo khi service down.

**Trong docker-compose.yml:**
```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
  interval: 10s
  retries: 5
```
