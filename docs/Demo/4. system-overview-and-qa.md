# University Portal — Tóm tắt hệ thống & Bộ câu hỏi ôn tập

> Tài liệu này dùng cho: thuyết minh miệng trước hội đồng + tự ôn luyện kiến thức hệ thống.

---

## I. TỔNG QUAN HỆ THỐNG (5 dòng)

University Portal là hệ thống quản lý đào tạo đại học được xây dựng theo kiến trúc Clean Architecture, gồm backend .NET 10 (C#) và frontend React 19 + TypeScript + Ant Design, kết nối với cơ sở dữ liệu SQL Server thông qua Entity Framework Core. Hệ thống phân quyền theo 4 vai trò: Admin, Giáo vụ, Giáo viên và Sinh viên, xác thực bằng JWT với cơ chế Refresh Token rotation để đảm bảo bảo mật. Các nghiệp vụ cốt lõi bao gồm: quản lý chương trình đào tạo, điểm số, biên bản sinh hoạt lớp, học phí, thông báo và yêu cầu hành chính. Toàn bộ hệ thống được đóng gói bằng Docker Compose, triển khai trên AWS EC2, với frontend phục vụ qua Nginx và API qua Kestrel port 8080. Với hơn 33 thực thể và 50+ endpoint RESTful, hệ thống đáp ứng đầy đủ vòng đời học tập của sinh viên từ nhập học đến tốt nghiệp.

**Câu 3: JWT là gì? Hệ thống dùng JWT như thế nào?**

> JWT (JSON Web Token) là chuẩn xác thực stateless. Hệ thống phát:
> - **Access Token** — sống ngắn (~60 phút), gắn vào header `Authorization: Bearer <token>` mỗi request
> - **Refresh Token** — sống dài (~7 ngày), lưu trong DB, dùng để lấy Access Token mới khi hết hạn
>
> Payload JWT chứa: `Id`, `Name`, `Role`, `HoTen`

### 🟡 PHẦN 2: KIẾN THỨC TRUNG CẤP (Câu 13–28)

---

**Câu 13: Refresh Token rotation là gì? Tại sao nên dùng?**

> Mỗi lần dùng Refresh Token để lấy Access Token mới, hệ thống sẽ **vô hiệu hóa Refresh Token cũ** và phát **Refresh Token mới**. Nếu kẻ tấn công đánh cắp Refresh Token, khi họ dùng thì token của user hợp lệ cũng bị invalidate → user phải đăng nhập lại → phát hiện được lộ token. Phòng chống **replay attack**.

---

**Câu 14: Luồng tính điểm tổng kết (DiemTongKet) hoạt động như thế nào?**

> Giáo viên nhập 3 thành phần điểm vào bảng `DanhSachLopHP`:
> - **DiemQt1** — Điểm quá trình 1 (thường hệ số 1)
> - **DiemQt2** — Điểm quá trình 2 (thường hệ số 1)
> - **DiemThi** — Điểm thi cuối kỳ (hệ số cao hơn)
>
> Hệ thống tự tính `DiemTongKet` theo công thức trọng số được cấu hình trong `ChiTietCTDT`.
> Giáo viên sau đó **khóa bảng điểm** (`KhoaBangDiem = true`) để chốt điểm chính thức.

**Câu 15: Chương trình đào tạo (ChuongTrinhDT) liên quan đến các entity nào? Mô tả chuỗi liên kết.**

> ```
> NganhHoc (Ngành học)
>     └── ChuongTrinhDT (Chương trình đào tạo — theo năm khoá học)
>             └── ChiTietCTDT (Chi tiết CTDT — từng môn học)

> `ChiTietCTDT` là bảng trung gian lưu thêm: số tín chỉ, cờ có tính điểm hay không, học kỳ dự kiến.

**Câu 16: Repository Pattern được triển khai như thế nào trong dự án?**

> - `BaseRepository<T>` — generic repository với CRUD cơ bản (GetById, GetAll, Add, Update, Delete)
> - Các repository cụ thể kế thừa `BaseRepository<T>` và thêm method đặc thù
>   - Ví dụ: `TaiKhoanRepository` có `FindByUsername()`, `SinhVienRepository` có `GetByMssv()`
> - Tất cả repo được lazy-init qua `UnitOfWork` và dùng chung **1 instance `AppDbContext`** per request

---

**Câu 17: Unit of Work Pattern giải quyết vấn đề gì? Hệ thống dùng nó ra sao?**

> **Vấn đề:** Khi 1 thao tác nghiệp vụ cần ghi vào nhiều bảng, phải đảm bảo **tất cả thành công hoặc tất cả thất bại** (atomic).
>
> **Giải pháp:** `IUnitOfWork` bọc tất cả repository, gọi `CommitAsync()` một lần duy nhất cuối request.
> Ví dụ: Tạo sinh viên → tạo TaiKhoan (repo1) + tạo SinhVien (repo2) → CommitAsync() → 1 transaction duy nhất.

---

**Câu 18: Middleware `GlobalExceptionMiddleware` xử lý lỗi như thế nào?**

> Đặt ở đầu pipeline, bắt **mọi exception** chưa được xử lý:
> - `BadRequestException` → HTTP 400
> - `NotFoundException` → HTTP 404
> - `ForbiddenException` → HTTP 403
> - Exception không xác định → HTTP 500
>
> Tất cả được format thành `ApiResponseDto` chuẩn trước khi trả về client. Giúp controller không cần try-catch.

---

**Câu 19: AutoMapper được dùng như thế nào trong hệ thống?**

> AutoMapper ánh xạ giữa **Entity ↔ DTO** (Data Transfer Object):
> - `Entity → ReadDto` — khi trả dữ liệu ra API
> - `CreateDto → Entity` — khi tạo mới
> - `UpdateDto → Entity` — khi cập nhật
>
> Config trong các `Profile` class ở layer Application. Inject `IMapper` vào service và gọi `_mapper.Map<TargetType>(source)`.

---

**Câu 20: FluentValidation được dùng để làm gì? Cho ví dụ.**

> Validate DTO đầu vào trước khi vào service/business logic. Ví dụ `CreateSinhVienValidator`:
> ```csharp
> RuleFor(x => x.HoTen).NotEmpty().MaximumLength(100);
> RuleFor(x => x.Mssv).NotEmpty().Matches(@"^\d{8}$");
> RuleFor(x => x.Email).EmailAddress();
> ```
> Tích hợp với ASP.NET Core: nếu validation fail → tự động trả 400 Bad Request với danh sách lỗi.

**Câu 21: Hệ thống thông báo (ThongBao) hoạt động như thế nào?**

> - `ThongBao` — lưu nội dung thông báo, loại (`LoaiThongBao`), mức độ (`MucDo`), có thể nhắm đến lớp cụ thể (`LopNhanId`) hoặc broadcast toàn hệ thống

> - `BinhLuanThongBao` — comment trên thông báo, cho phép thảo luận 2 chiều

**Câu 22: Biên bản sinh hoạt lớp (BienBanSHCN) ghi nhận những gì?**

> Mỗi `BienBanSHCN` gắn với 1 tuần học (`TuanHoc`), ghi lại:
> - Ngày họp, địa điểm, nội dung họp
> - **Điểm danh vắng** (`ChiTietVangSHCN`) — sinh viên nào vắng, có phép hay không
> - **Phân công công việc** (`ChiTietCongViec`) — task giao cho sinh viên
> - **Phản hồi GVCN** (`PhanHoiGvcn`) — nhận xét, kiến nghị của chủ nhiệm
> - Thư ký lớp (`ThuKy`) hỗ trợ ghi chép

**Câu 23: Sinh viên có thể làm gì khi phát hiện điểm sai?**

> 1. Sinh viên gửi `YeuCauSuaDiem` — yêu cầu sửa điểm, kèm lý do và điểm đề nghị
> 2. Giáo viên nhận thông báo, xem xét yêu cầu
> 3. Nếu chấp nhận: giáo viên mở khóa bảng điểm (`KhoaBangDiem = false`), sửa điểm, khóa lại
> 4. Nếu từ chối: trả lời lý do từ chối về phía sinh viên
> 5. Trạng thái request được cập nhật theo luồng xử lý

---

**Câu 24: State management ở frontend dùng gì? Dữ liệu auth được persist như thế nào?**

> **Zustand 5** làm state management, tối giản hơn Redux.
>
> Store `useAuthStore` lưu: `accessToken`, `refreshToken`, `user` (id, hoTen, vaiTro).
>
> Dữ liệu được **persist vào `localStorage`** với key `university-portal-auth` → user không phải đăng nhập lại khi refresh trang.

---

**Câu 25: Axios interceptor ở frontend hoạt động như thế nào?**

> **Request interceptor** — tự động gắn `Authorization: Bearer <accessToken>` vào header mọi request.
>
> **Response interceptor** — nếu nhận lỗi 401 (token hết hạn):
> 1. Gọi `POST /auth/refresh` với Refresh Token
> 2. Nhận Access Token mới, cập nhật store
> 3. **Retry** request gốc với token mới — user không nhận ra gián đoạn
> 4. Nếu refresh cũng lỗi → logout, redirect về trang đăng nhập

---

**Câu 26: ProtectedRoute ở frontend kiểm soát truy cập như thế nào?**

> Component `ProtectedRoute` nhận prop `allowedRoles: string[]`.
> Khi user truy cập route:
> 1. Kiểm tra có `accessToken` không → nếu không, redirect `/login`
> 2. Kiểm tra `user.vaiTro` có nằm trong `allowedRoles` không → nếu không, hiển thị 403 Forbidden
> 3. Nếu đủ điều kiện → render component con

---

**Câu 27: Tại sao dùng `AuditableEntity` làm base class cho tất cả entity?**

> `AuditableEntity` chứa 4 trường:
> - `CreatedAt` — thời điểm tạo (tự set khi Insert)
> - `UpdatedAt` — thời điểm cập nhật cuối (tự set khi Update)
> - `CreatedBy` — người tạo
> - `UpdatedBy` — người cập nhật cuối
>
> Tất cả entity kế thừa → tự động có audit log mà không cần viết lại. EF Core override `SaveChangesAsync()` để tự điền giá trị này.

---

**Câu 28: CORS được cấu hình như thế nào? Có vấn đề bảo mật gì không?**

> Hiện tại cấu hình:
> ```csharp
> .AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader()
> ```
> **Vấn đề:** Cho phép mọi domain gọi API — phù hợp môi trường dev/staging, **KHÔNG an toàn cho production**. Production nên whitelist domain cụ thể:
> ```csharp
> .WithOrigins("https://portal.university.edu.vn")
> ```

### 🔴 PHẦN 3: KIẾN THỨC NÂNG CAO (Câu 29–42)

---

**Câu 29: Giải thích tại sao Clean Architecture giúp dễ bảo trì và mở rộng hơn?**

> **Nguyên tắc cốt lõi:** Dependency chỉ đi vào trong (từ ngoài → trong):
> - Domain không biết Application, Infrastructure, API
> - Application chỉ biết Domain
> - Infrastructure và API phụ thuộc vào các layer trong
>
> **Lợi ích thực tế:**
> - Đổi database (SQL Server → PostgreSQL) chỉ cần sửa Infrastructure, không động đến business logic
> - Thêm REST API hoặc gRPC endpoint mà không đụng service layer
> - Unit test service/business logic dễ dàng bằng cách mock interface (không cần DB thật)

**Câu 30: Token Refresh race condition là gì và xử lý như thế nào?**

> **Vấn đề:** Nếu nhiều request đồng thời nhận lỗi 401, tất cả đều cố refresh token → chỉ request đầu tiên thành công, các request sau dùng token cũ đã bị rotate → thất bại liên tục.
>
> **Giải pháp thường dùng:**
> - Frontend: dùng **promise queue** — chỉ cho 1 refresh request chạy, các request khác chờ (pending queue)
> - Khi refresh xong, resolve tất cả pending request với token mới

**Câu 31: Soft delete được cài đặt như thế nào? Ảnh hưởng đến query như thế nào?**

> Soft delete dùng flag `IsDeleted = true` (hoặc `DeletedAt`) thay vì xóa khỏi DB.
>
> Để tự động lọc record đã xóa, EF Core dùng **Global Query Filter**:
> ```csharp
> modelBuilder.Entity<SinhVien>().HasQueryFilter(x => !x.IsDeleted);
> ```
> Mọi query qua EF Core tự động thêm `WHERE IsDeleted = 0` → code service/repo không cần lọc thủ công.
> Để xem record đã xóa, dùng `.IgnoreQueryFilters()`.

**Câu 32: Giải thích vấn đề N+1 query trong EF Core và cách tránh.**

> **N+1 problem:** Truy vấn 1 list (1 query) rồi với mỗi item lại query thêm navigation property (N queries).
> ```csharp
> // BAD: N+1
> var students = await context.SinhViens.ToListAsync(); // 1 query
> foreach (var s in students) { var lop = s.LopSinhHoat; } // N queries
>
> // GOOD: Eager loading
> var students = await context.SinhViens
>     .Include(s => s.LopSinhHoat)
>     .ToListAsync(); // 1 query với JOIN
> ```
> Dùng `.Include()` / `.ThenInclude()` để eager load, hoặc `.Select()` để projection chỉ lấy field cần.

**Câu 33: Validation ở service layer có cần thiết không khi đã có FluentValidation ở controller?**

> **Có, cần cả hai:**
> - **FluentValidation (API layer)** — kiểm tra format, required fields, length... Chặn trước khi vào service
> - **Validation ở service layer** — kiểm tra **business rule**: sinh viên đã đăng ký môn này chưa? GVCN được phân công cho lớp khác chưa? Môn học có trong chương trình không?
>
> Lý do: Service layer có thể được gọi từ nhiều nguồn (API, background job, unit test) → business rule phải được enforce ở service, không chỉ ở API layer.

**Câu 34: Chiến lược migration database là gì trong dự án? Có rủi ro gì không?**

> Dự án dùng **auto-migration on startup** (Program.cs):
> ```csharp
> await dbContext.Database.MigrateAsync();
> ```
> Chạy tất cả migration pending khi ứng dụng khởi động.
>
> **Rủi ro:**
> - Migration chạy đồng thời nhiều instance → race condition (cần distributed lock)
> - Migration thất bại giữa chừng → DB state không nhất quán
>
> **Best practice cho production:** Tách migration thành job riêng hoặc CI/CD step, không chạy auto trong app startup.

**Câu 35: GPA tích lũy (DiemTbcTichLuy) trong HocBa được tính như thế nào?**

> GPA tích lũy = **Trung bình có trọng số** (weighted average) theo tín chỉ:
>
> ```
> GPA = Σ(DiemTongKet_môni × SoTinChi_môni) / Σ(SoTinChi_môni)
> ```
>
> Chỉ tính các môn thuộc `ChuongTrinhDT` của sinh viên, theo flag `TinhDiem` trong `ChiTietCTDT`.
> `HocBa.SoTinChiTichLuy` = tổng tín chỉ các môn đã qua (DiemTongKet ≥ ngưỡng đỗ).

**Câu 36: Tại sao dùng Dependency Injection (DI) thay vì khởi tạo service trực tiếp?**

> **Lý do:**
> 1. **Testability** — inject mock/fake trong unit test mà không cần instance thật
> 2. **Loose coupling** — class phụ thuộc vào interface, không phụ thuộc implementation cụ thể
> 3. **Lifetime management** — DI container quản lý Singleton/Scoped/Transient tự động
> 4. **Extensibility** — đổi implementation chỉ cần sửa DI registration, không sửa code dùng nó
>
> Trong project: `AddApplication()` và `AddInfrastructure()` là extension methods đăng ký tất cả services/repos.

**Câu 37: Hệ thống xử lý concurrent grade update như thế nào? (Optimistic vs Pessimistic locking)**

> Hiện tại hệ thống dùng cơ chế **KhoaBangDiem flag** (Pessimistic-style ở business level):
> - Khi `KhoaBangDiem = true`, API từ chối mọi request sửa điểm
> - Chỉ giáo viên phụ trách mới có thể mở/khóa
>
> **Thiếu xót tiềm ẩn:** Không có **row-level optimistic concurrency** (EF Core `RowVersion`/`ConcurrencyToken`). Nếu 2 giáo viên cùng sửa 1 record đồng thời (unlikely nhưng có thể), người sau ghi đè người trước mà không có cảnh báo.

**Câu 39: Chiến lược index database nào nên được áp dụng cho bảng DanhSachLopHP?**

> `DanhSachLopHP` là bảng được query nhiều nhất (điểm sinh viên). Nên có index:
> ```sql
> -- Query phổ biến nhất: lấy điểm 1 sinh viên trong 1 lớp học phần
> CREATE INDEX IX_DanhSachLopHP_SinhVienId_LopHocPhanId
>     ON DanhSachLopHP (SinhVienId, LopHocPhanId);
>
> -- Query: tất cả sinh viên trong 1 lớp học phần (giáo viên nhập điểm)
> CREATE INDEX IX_DanhSachLopHP_LopHocPhanId
>     ON DanhSachLopHP (LopHocPhanId);
> ```
> EF Core tự tạo index cho foreign key nhưng composite index cần cấu hình thủ công.

**Câu 40: Nếu hệ thống cần scale lên 10.000 sinh viên đồng thời, cần cải thiện gì?**

> **Các điểm nghẽn cổ chai và giải pháp:**
>
> 1. **Database connection pool** — cấu hình `Min/MaxPoolSize` trong connection string
> 2. **Read-heavy endpoints** — thêm **Redis caching** cho thời khóa biểu, danh mục môn học (ít thay đổi)
> 3. **Static files** — đưa ảnh đại diện lên **CDN/S3** thay vì lưu local volume
> 4. **JWT validation** — hiện stateless → scale ngang API dễ dàng, không cần session sticky
> 5. **Notification broadcast** — chuyển sang **SignalR** hoặc message queue (RabbitMQ/Azure Service Bus)
> 6. **Database** — xem xét Read Replica cho query nặng (báo cáo, thống kê)

**Câu 41: Tại sao lại dùng `IUnitOfWork` interface thay vì inject `AppDbContext` trực tiếp vào service?**

> **Lý do kỹ thuật:**
> - `AppDbContext` là implementation detail của Infrastructure layer — service ở Application layer không nên biết đến EF Core
> - `IUnitOfWork` là **abstraction** — service chỉ biết "có thể commit transaction", không biết dùng EF, Dapper hay raw SQL
> - **Testability** — mock `IUnitOfWork` trong unit test dễ hơn mock `DbContext`
> - **Flexibility** — có thể đổi từ EF Core sang Dapper chỉ bằng cách đổi Infrastructure, không sửa service
>
> **Nguyên tắc:** Application layer phụ thuộc vào *abstraction* (interface), Infrastructure phụ thuộc vào *implementation*.

**Câu 42: Mô tả một lỗ hổng bảo mật tiềm ẩn trong hệ thống và cách khắc phục.**

> **Lỗ hổng: Insecure Direct Object Reference (IDOR)**
>
> **Tình huống:** Sinh viên A (id=1) gọi `GET /sinh-vien/2` → có thể xem thông tin sinh viên B.
>
> **Cách khắc phục:**
> ```csharp
> // Trong controller, sau khi xác thực JWT:
> var currentUserId = User.FindFirst("Id")?.Value;
> var currentRole = User.FindFirst("Role")?.Value;
>
> if (currentRole == "SinhVien" && id.ToString() != currentUserId)
>     throw new ForbiddenException("Không có quyền xem thông tin người khác");
> ```
> Ngoài ra: luôn validate ownership ở service layer, không chỉ dựa vào role. Sinh viên chỉ nên xem được dữ liệu của chính mình (điểm, học bạ, yêu cầu).
